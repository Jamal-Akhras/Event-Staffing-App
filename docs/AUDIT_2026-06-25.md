# Production-Grade Audit — Event Staffing Platform

**Date:** 2026-06-25
**Scope:** FastAPI backend (`apps/api`), React web (`apps/web`), Expo mobile (`apps/mobile`), data layer, CI, repo hygiene.
**Reviewer perspective:** Senior software engineer, pre-production readiness.

---

> **Status update (July 2026):** the High findings below have been fixed and regression-tested since this audit: H1 via corrected DI wiring plus `test_no_show_sweep_entrypoints.py`, H2 via invite-code gating (`operator_invites.py`, `test_operator_invite_gating.py`) and email verification (`test_email_verification.py`). Several Medium items are also addressed, including JWT revocation (`test_token_revocation.py`) and upload validation. The audit is preserved as-written.

## Executive summary

This is a well-structured codebase. The domain is cleanly separated (domain / repositories / services / routes), the data model has strong integrity constraints, the hard concurrency problem (multi-worker shift capacity under concurrent approvals) is solved correctly with row locks inside a transaction, and there are sensible startup guardrails for production secrets. Frontend error handling is genuinely good.

However, it is **not yet production-ready**. There is one confirmed functional defect that silently disables a headline reliability feature, an open privilege-granting registration endpoint, and a rate-limiting setup that does not work behind a load balancer. Details and priorities below.

## Critical / High

### H1 — No-show sweep is dead in both background entrypoints (confirmed)
The scheduled job and the one-off CLI job both call the sweep with the wrong number of arguments. `sweep_no_shows()` and `BookingLifecycleService.__init__` were extended to take `shift_repo`, but these two callers were never updated:

- `apps/api/src/scheduler.py:20` — `BookingLifecycleService(booking_repo, worker_repo)` → missing `shift_repo` → `TypeError`.
- `apps/api/src/jobs/run_no_show_sweep.py:20` — `sweep_no_shows(booking_repo, worker_repo, now)` → `now` binds to `shift_repo`, real `now` missing → `TypeError`.

Both errors are swallowed by broad `except Exception` blocks and only logged, so the worker process appears healthy while **no-shows are never swept** — reliability scores never update from no-shows in normal operation. The only working path is the `POST /system/no-show-sweep` endpoint (used by tests via the 3-arg DI wiring), which is why the test suite is green: tests call the underlying functions directly with the correct signature (`test_no_show_sweep_service.py:54`) and never import `scheduler.py` or `jobs/run_no_show_sweep.py`.

**Fix:** pass `SqlAlchemyShiftRepository(session)` in both callers; add a smoke test that actually invokes `scheduler.run_no_show_sweep` and `jobs.run_no_show_sweep.run`.

### H2 — Open operator self-registration grants venue privileges with no verification
`POST /auth/register/operator` (`apps/api/src/routes/auth.py:100`) is public and creates an `operator` account + venue with only a rate limit. There is no email verification and no invite/approval. Operators can post shifts and view applicant data. README history implies operators were meant to be created via the `create_operator` CLI; the open endpoint is a privilege-granting surface. Confirm this is intentional; if not, gate it behind invite/verification. Separately, no registration path verifies email ownership at all.

## Medium

### M1 — Rate limiting does not hold up in production topology
`apps/api/src/rate_limit.py` uses slowapi with **in-memory** storage and `get_remote_address`. Two consequences behind a reverse proxy / multiple instances:
- Per-process, lost on restart, not shared across replicas — limits are effectively `limit × replicas` and reset on every deploy.
- `get_remote_address` keys on the socket peer IP. Behind a proxy/load balancer every request appears to come from the proxy IP, so all users collapse into one bucket — login brute-force protection becomes either a shared self-DoS or trivially bypassable depending on topology.

**Fix:** use a shared store (e.g. Redis) and derive the client IP from a trusted `X-Forwarded-For` (with a trusted-proxy allowlist).

### M2 — JWTs are non-revocable and stored in `localStorage`
Tokens are 24h, carry no `jti`, and there is no server-side blacklist — logout is client-only and a leaked token is valid until expiry. The web app stores the token in `localStorage` (`apps/web/src/contexts/AuthContext.tsx`, `lib/api.ts:40`), which is readable by any injected script (XSS → token theft). Consider httpOnly cookies or, at minimum, a strict CSP plus short-lived access tokens with refresh + revocation.

### M3 — File uploads: full read before size check, extension-only validation
`apps/api/src/routes/uploads.py` does `data = await file.read()` and *then* checks `len(data) > _MAX_BYTES`. A large upload is fully buffered into memory before rejection — a memory-exhaustion DoS vector. Validation is also extension-only (no magic-byte/content check, no re-encode), and files are served back via `StaticFiles`. **Fix:** enforce size during streaming (or via `Content-Length`/`file.size`), validate real content type, and re-encode images.

### M4 — `run_recurring_generation` mishandles session state on error
`apps/api/src/scheduler.py:62-84`: on an exception inside the per-schedule loop it logs but does **not** `session.rollback()`, so the session stays in a failed-transaction state and subsequent iterations also fail. It also sets `last_generated_at = lookahead` (a *future* timestamp), which interacts awkwardly with the `last_generated_at > now + 7d` skip guard. Wrap each schedule in its own try/rollback and reconsider the watermark logic.

### M5 — Synchronous, globally-serialized geocoding in the request path
`apps/api/src/services/geocoding.py` makes a blocking HTTP call to Nominatim under a global lock with `time.sleep` up to 1s. If called during shift creation it serializes all geocoding across the whole process and blocks a worker thread for up to ~4s (sleep + 3s timeout). Nominatim's usage policy (1 req/s, no heavy production use, no key) also risks IP bans. **Fix:** move geocoding off the request path (background/queue), cache results in the DB, or use a commercial geocoder.

### M6 — Repos without in-memory fallback break documented in-memory mode
`get_account_repo`, `get_notification_repo`, `get_rating_repo` (`apps/api/src/deps.py:224-245`) always open a SQLAlchemy session, unlike every other repo which honors `_use_in_memory()`. In the documented `USE_IN_MEMORY`/no-`DATABASE_URL` mode these endpoints hit a DB that may not exist or be migrated — inconsistent behavior and latent runtime errors.

### M7 — CI never exercises the production data path
`.github/workflows/ci.yml` spins up Postgres and runs migrations, but sets `USE_IN_MEMORY: "true"`, so all API-level tests run against in-memory repositories. The SQLAlchemy adapters and the row-locking concurrency logic — the actual production code path — are only covered by direct unit tests, not through the API. This is precisely the gap that let H1 ship green. Add a CI job (or matrix leg) that runs the endpoint tests against Postgres with `USE_IN_MEMORY=false`.

## Low

- **L1 — `edy.py` at repo root** contains `print("edy is gay")`. Junk and inappropriate; delete it and the stray root log files (`*.out.log`, `*.err.log`) if any are tracked.
- **L2 — Re-booking after cancellation is impossible.** `uq_bookings_worker_shift` means once a worker has any booking for a shift (incl. cancelled/no-show), re-approval raises `IntegrityError` → 409. Confirm intended; if not, scope uniqueness to active states.
- **L3 — AGENTS.md rules violated.** "No empty try/catch", "no default fallbacks" — several `except Exception: pass` (geocoding `_fetch`, `_notify_decision`, scheduler jobs) swallow errors silently.
- **L4 — Doc drift.** README says "migrations run through 009" but the tree has migrations through 018; mobile "planned" 4-tab nav already exists as screens. Refresh README.
- **L5 — Frontend status mismatch.** `api.ts:164` maps the register-conflict message to HTTP 409, but the backend returns 400 for "Email already registered" (`auth.py:46,113`). The friendly message never shows. Align them.
- **L6 — `/auth/me` mislabels auth mode.** `get_bool_env("DEV_MODE", True)` (`auth.py:196`) defaults to `True`, inconsistent with the `False` default used everywhere else; cosmetic but misleading.
- **L7 — Password reset tokens are reusable** within their 1h window (no `jti`/single-use); only invalidated once the password actually changes. Acceptable for MVP, not best practice.

## What's done well (keep it)

- Clean layering and a real repository pattern with paired in-memory + SQLAlchemy adapters.
- **Correct concurrency on the capacity-critical path**: `approve()` takes `with_for_update()` locks on application and shift inside a single transaction and re-checks capacity — the genuinely hard part, done right (`sqlalchemy_application_decision_repository.py`).
- Strong schema integrity: CheckConstraints, UniqueConstraints, FKs with explicit `ondelete`, and indexes on hot columns (`db/models.py`).
- Production startup guardrails reject the default JWT secret / short secrets / `DEV_MODE` outside development (`config.py`, `auth/jwt.py`).
- bcrypt hashing, JWT auth, rate-limited auth endpoints, role/ownership checks consistently applied per route (IDOR-resistant).
- Solid frontend API client: typed errors, friendly messages, 401 handling, network-error handling.
- Multi-stage Dockerfile running as a non-root user; healthchecks and dependency ordering in compose.
- Decimal-based money math in the payments quote calculator (which is quote-only — no money movement, good).
