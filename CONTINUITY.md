- 2026-08-28 D067 ACTIVE [USER] Money is frozen at approval, not recomputed on read. - 2026-08-28 D066 ACTIVE [USER] Every booking state change writes a `booking_transitions` row recording who caused it (user id and role, including `system` for the no-show sweep), when, from and to which state, and a reason code drawn from a fixed list enforced at both the schema edge and a database CHECK. - 2026-08-28 D065 ACTIVE [USER] Feed measurement is defined in three tiers, not one: `shift.served` is recorded server-side when the feed API includes a shift (the complete denominator), `shift.viewed` means at least 50% of the card was on screen for at least one continuous second, and `shift.dwelled` means 75% for two seconds. - 2026-08-28 D064 ACTIVE [USER] Track everything: one append-only `events` table is the system of record for auditability and analysis. Three writers feed it — an audit middleware that records every mutating HTTP request (actor, route template, status, duration, request id, ip, client, session), semantic lifecycle hooks in routes (every booking transition, application created/approved/rejected/withdrawn, auth login and login_failed), and a rate-limited `POST /events` batch ingest so web and mobile can send behaviour. Events carry category (audit|lifecycle|behaviour|auth|money|system), actor, venue/worker scope, subject, JSON context, and client metadata. Secrets are redacted by key name and context is capped at 4KB; request bodies are never recorded. Lifecycle events are written in the request transaction so they only exist if the change committed, while audit and auth-failure events are written on their own session so a rolled-back or rejected request still leaves a trail. Read paths: `GET /system/events` and `/system/events/counts` for staff, `GET /activity` scoped to the caller's venue or worker record. No update or delete path exists, and PostgreSQL revokes UPDATE/DELETE on the table from PUBLIC.
