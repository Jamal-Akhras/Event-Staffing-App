## Decisions
- 2026-09-02 D072 ACTIVE [USER] Insight is positive-first everywhere, not only on Analytics, extending D059. Framed as opportunity and next action, never blame: lead with what is working, keep failures visible and explained but never the largest number on the page, and write healthy empty states as achievements ("every shift covered this month", not a blank chart). The driver is that these screens double as sales material — they are shown to prospective venues before those venues have any data — so a venue must feel capable, not audited. Consumer hiring is a possible later direction, not a design driver; only four structural rules are kept for it, each justified by a customer the product already serves. Requirements in `documentation/00-product/workforce-requirements.md`.
- 2026-09-01 D071 ACTIVE [USER] The product pivots from a one-off temp marketplace to a workforce management tool: a venue organises its permanent staff, its own pool and one-off temps in one place, schedules them, sees what they cost, and gets combined statements. Scope is management and scheduling, not HR — no contracts, documents or performance. Placements stay shift by shift; "employment agency" describes the legal posture, not booking length. **Wages never pass through the app for anyone, permanent or temp**, which settles the agency-versus-employment-business question left open by the legal review. Venues pull approved hours out as a timesheet export and run their own payroll — the platform never pushes into a payroll portal, which the Conduct Regulations treat as arranging payment. Pricing follows a Limber-style structure: Classic £0 + 10%, Plus from £25/site with 0% on your own pool and 10% outside it, Enterprise custom; permanent workers are free under the monthly fee. One worker app with a relationship-dependent home. Plan and action items in `documentation/00-product/workforce-pivot-plan.md`.
- 2026-08-30 D070 ACTIVE [USER] Worker settings follow the platform convention rather than the console's: a grouped list that drills into pushed detail screens, not tabs. Tabs are a large-screen pattern that both iOS and Android collapse into a hierarchy on a phone, and a horizontally scrolling tab strip is the worst version because options off-screen may as well not exist. Every row carries its current value on the right so the list answers before a tap. `@react-navigation/native-stack` was added on the v6 line to match the existing `@react-navigation/native@6`; npm's default v7 was refused rather than dragging in a major upgrade. The Profile tab keeps its two-way segmented control (How venues see you / Settings) because those are peers.
- 2026-08-30 D069 ACTIVE [USER] The worker app is a rebuild, not a patch, and it inherits the operator console's visual language: Space Grotesk, `--ocean-500` on warm papers, 12/16 radii. Three rules make it read as a considered product rather than a startup: the accent appears once per screen and only on the primary action; status is a word plus a small mark, never a filled coloured pill; type sits at weight 400-500 with hierarchy from size, spacing and colour. Money is set in tabular figures with the currency symbol lighter than the value. Tabs are Browse · Shifts · Applications · Earnings · Profile — Shifts holds work you have (Upcoming, Previous), Applications holds work you asked for (Waiting, Decided). Notifications are a header bell with a badge, not a tab.
- 2026-08-28 D068 ACTIVE [USER] Figures are computed by the server, lists are paginated by the client. Every headline number a venue reads — open seats per day, applications waiting and their oldest arrival, attendance over thirty days, and per-worker completed shifts, last worked and recent no-shows — comes from `GET /insights/overview` and `GET /insights/roster`, which aggregate in SQL over the venue's whole history. Anything scoped to a window (a board week, a month, a worker's recent shifts) is bounded by a date range through `starts_from`/`starts_before` on `/shifts`, never by a row count. Queues an operator works through — pending applications, bookings behind a modal — stay paginated lists, but the count beside them is the true total, not the length of the page.
- 2026-08-28 D067 ACTIVE [USER] Money is frozen at approval, not recomputed on read. Approving a completed booking writes one immutable `booking_charges` row holding the hours worked, the pay rate in force at that moment, wages, the fee percentage, the fee, the total, the currency, and the worker name and role as they then read. The billing statement reports those rows and never recalculates from live shift data, so editing a shift's pay rate or renaming a worker afterwards cannot rewrite an invoice that has already been shown. Only payment status stays live, because it genuinely changes after approval. Partner-code waivers are decided at freeze time and consume the cap in approval order, matching the existing rule that a redemption covers shifts completed after it.
- 2026-08-28 D066 ACTIVE [USER] Every booking state change writes a `booking_transitions` row recording who caused it (user id and role, including `system` for the no-show sweep), when, from and to which state, and a reason code drawn from a fixed list enforced at both the schema edge and a database CHECK. The booking keeps its current-state column; the table is the history beside it. Idempotent repeat calls, which the state machine allows, record nothing — a retry is not a state change. History is readable at `GET /bookings/{id}/transitions`, scoped to the owning venue or the worker.
- 2026-08-28 D065 ACTIVE [USER] Feed measurement is defined in three tiers, not one: `shift.served` is recorded server-side when the feed API includes a shift (the complete denominator), `shift.viewed` means at least 50% of the card was on screen for at least one continuous second, and `shift.dwelled` means 75% for two seconds. What the client renders is not an impression. Every feed event carries `slate_id` and `position` because the ranking that produced a list cannot be reconstructed later, and every client event carries `event_version` because old app versions keep emitting old shapes into an append-only log. "Filled" means checked in, not approved, and fill rate is always reported with its denominator stated.
- 2026-08-28 D064 ACTIVE [USER] Track everything: one append-only `events` table is the system of record for auditability and analysis. Three writers feed it — an audit middleware that records every mutating HTTP request (actor, route template, status, duration, request id, ip, client, session), semantic lifecycle hooks in routes (every booking transition, application created/approved/rejected/withdrawn, auth login and login_failed), and a rate-limited `POST /events` batch ingest so web and mobile can send behaviour. Events carry category (audit|lifecycle|behaviour|auth|money|system), actor, venue/worker scope, subject, JSON context, and client metadata. Secrets are redacted by key name and context is capped at 4KB; request bodies are never recorded. Lifecycle events are written in the request transaction so they only exist if the change committed, while audit and auth-failure events are written on their own session so a rolled-back or rejected request still leaves a trail. Read paths: `GET /system/events` and `/system/events/counts` for staff, `GET /activity` scoped to the caller's venue or worker record. No update or delete path exists, and PostgreSQL revokes UPDATE/DELETE on the table from PUBLIC.
